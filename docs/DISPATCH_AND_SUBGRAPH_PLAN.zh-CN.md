# Hexagon 算子派发与子图编译方案

日期：2026-11-11  
状态：设计提案，尚未实施；本文不代表新运行时已完成或性能已验收。

## 1. 要解决什么问题

当前路径将 Qwen3 模型前向提前编译、链接为 `model.so`，运行时调用其前向入口。已有算子、融合内核和 DSP 驻留 KV 可以继续使用，但模型执行组织与模型专用构建流程耦合较深。

本方案将执行组织改为：计算图生成执行计划，运行时根据计划调用通用算子或编译后的融合子图。目标是便于适配模型、替换内核及调整调度，减少对完整模型重新编译的依赖。

这项架构改造不会自动消除算子与 llama.cpp 的性能差距。必须分别衡量内核性能、运行时开销和端到端收益。

## 2. 几个概念的区别

| 概念 | 含义 |
| --- | --- |
| 算子派发（dispatch） | 根据算子、形状、数据类型、布局等选择具体实现 |
| 子图拆分 | 将计算图划分为可独立编译或执行的部分 |
| 算子融合 | 将多个运算合成一个实现，减少中间读写或调用开销 |
| 整图编译 | 编译器处理完整计算图，产物仍可以包含多个内核及调用代码 |
| Megakernel | 通常指一个设备端内核承担很大范围的计算或设备端调度 |

当前 `model.so` 是共享库文件，包含前向执行入口和多个算子或融合内核。一次调用完成整个前向，不等于整个模型融合成了一个 megakernel。

子图拆分也不同于提示词分块：前者划分计算过程，后者划分本次处理的 token 数量。

## 3. 与 llama.cpp Hexagon 的区别

本地参考实现位于 `/home/kevin/llamacpp-hexagon`。

其 `ggml/src/ggml-hexagon/ggml-hexagon.cpp` 中的 `ggml_backend_hexagon_graph_compute` 会处理图节点、尝试融合、映射算子、缓存节点信息，随后入队执行并等待完成。

其 `ggml/src/ggml-hexagon/htp/CMakeLists.txt` 将矩阵乘、Attention、RoPE 等源码编译为 `libggml-htp-v*.so` 一类通用 DSP 库。这不同于为具体模型构建我们的 `model.so`。

值得借鉴的是通用内核复用、执行计划复用、批量提交和设备端内存管理。算子派发并不要求每个算子都进行一次 ARM/DSP 往返同步。

## 4. 建议架构

```text
PyTorch 模型
    │
    ▼
图捕获入口（torch.compile 或 export，首版选定一种）
    │
    ▼
图整理、支持范围检查、融合识别、子图划分
    │
    ▼
执行计划：内核选择 + 张量连接 + 缓冲区生命周期 + 状态依赖
    │
    ├── 已支持算子 ────────────► 复用预编译内核
    │
    └── 需要编译的融合子图 ────► torch-mlir / Hexagon-MLIR
                                    │
                                    ▼
                              编译产物及缓存
    │
    ▼
ARM 批量提交执行计划
    │
    ▼
DSP 执行器
    ├── 调用通用算子或融合子图
    ├── 复用线程池、工作区和预打包权重
    └── 原位更新驻留 KV，按有效长度计算
```

先在当前自定义后端内部实现派发即可。让任意 PyTorch eager 算子直接运行在 Hexagon 上，还需要完整的设备、张量分配、拷贝和算子注册支持，不属于首版范围。

MLIR 仍负责算子或子图的编译优化与代码生成。已有实现可直接复用，新形状或新子图可能仍需编译；不能承诺所有新模型都无需编译。

## 5. 需要实现的六项能力

| 能力 | 需要新增或整理的内容 | 可复用部分 |
| --- | --- | --- |
| 统一算子接口 | 输入输出描述、形状、步长、布局、量化参数、工作区要求、别名和修改语义 | 已优化算子及融合内核，必要时增加接口适配 |
| 内核注册与选择 | 按形状、布局、精度和有效 KV 长度选择实现；明确支持范围与失败行为 | 当前模型构建中的部分内核选择逻辑 |
| 执行计划 | 将图转为内核调用、缓冲区引用和依赖关系；缓存并检查适用条件 | 图捕获、AOT 整理、MLIR 降低流程 |
| DSP 执行器 | 批量提交、设备端调度、完成通知、错误返回、逐内核计时 | 现有会话、通信及线程管理设施，经接口核对后复用 |
| 内存与 KV 管理 | 缓冲区生命周期、权重预打包复用、工作区复用、KV 容量与有效长度分离 | 当前权重打包和驻留 KV 机制 |
| 子图划分与融合 | 支持能力判断、模式识别、状态依赖检查、跨子图布局衔接 | 已有融合内核和编译变换；仍需新增通用组织逻辑 |

### 接口必须表达的约束

- 张量数据类型、形状、步长、布局和量化比例必须明确，不能依赖模型专用的隐含假设。
- 区分只读权重、临时激活、可修改 KV；明确输入输出是否允许共享内存。
- KV 更新必须先于读取该位置的 Attention；请求重置必须清除逻辑状态，避免跨请求污染。
- 传入真实有效长度；容量只是分配上限，不应强制每次计算全部容量。
- 首版保持当前已支持的范围，不顺带增加 batch、多请求调度或任意模型支持。
- 不支持的算子或形状明确报错；CPU 回退若未来加入，应显式配置并记录，避免掩盖性能和执行位置问题。

### 内存与调度原则

中间结果留在设备可访问的缓冲区中，跨算子直接复用，不逐节点传回 ARM。物理共享内存也可能需要缓存一致性操作，这部分不能视为免费。

权重在装载时准备并复用，工作区按执行计划分配。KV 持续驻留，正常推理只交换必要输入和结果。同步按数据依赖和批次边界安排，避免每个算子都等待。

先实现顺序执行和明确依赖，再考虑并行调度。融合以减少实测开销为依据，避免一开始就编写复杂的通用优化器。

## 6. 代码放在哪里

| 仓库 | 职责 |
| --- | --- |
| `pytorch-hexagon` | PyTorch 接入、图到执行计划的适配、运行时调度与会话、模型配置、模型 KV 策略、端到端验证 |
| `hexagon-mlir` | 通用编译变换、目标代码生成、算子或子图编译支持，以及必须与编译器 ABI 配套的底层运行时支持 |

Qwen3 的层数、权重映射和模型专用规则留在应用仓库的模型目录。执行计划格式和内核调用接口尽量不依赖 Qwen3。通用优化只有在依赖和测试范围明确时才进入编译器仓库。

不为这次改造再创建一个重复的框架仓库，也不先移动所有现有文件。先做出最小可运行路径，再依据实际依赖提取公共代码。

## 7. 分阶段实施

### 阶段一：单层执行计划

选择一个 Qwen3 decoder 层，复用现有内核和精度策略，将当前调用流程表示为执行计划。保持权重和 KV 驻留，批量提交执行，不引入新的算术优化。

产物：接口约定、最小内核注册表、DSP 执行入口，以及单层运行示例。原有整模型入口保留作为对照和回退路径。

### 阶段二：严格比较执行组织开销

在同一设备、相同输入、相同内核和线程配置下，对比原有路径与执行计划路径。将编译、装载、首次准备、稳态执行分别记录。

测量内核时间、ARM 提交时间、同步等待、搬运或一致性操作、分配与布局转换。异步阶段可能重叠，不能将所有计时简单相加作为端到端时间。

逐层输出和 KV 校验单独运行，不放入正式计时区间。若只是组织方式改变，优先检查逐位一致；若内核或计算顺序改变，需另行制定误差与模型质量验收，不能混为同一项改造。

### 阶段三：完整模型和必要融合

将执行计划扩展到 28 层，复用已有融合实现。覆盖 prefill、decode、有效 KV 长度变化和请求重置。

之后根据 profiling 选择新的融合边界。SiLU 与乘法、归一化周边处理等只是候选，是否实施取决于中间读写、调用成本和寄存器或工作区压力，不能预先保证收益。

## 8. 验收条件与调整机制

- **正确性：** 同输入比较层输出、最终 logits 和 KV；执行短生成、请求重置及长度边界检查。通过组织改造的等价性检查，不等于模型整体质量已验收。
- **可复用性：** 同一支持范围内，不同 token 内容不触发重新编译；形状超出范围时明确选择其他实现、编译新版本或拒绝。
- **性能：** 同内核对照应能说明新增派发成本。重复短测确认差异是否超过噪声，再决定是否扩大改造；不能只凭某个内核更快宣称端到端更快。
- **可诊断性：** 执行计划可查看算子、形状、布局和内核选择；利用已有 Qualcomm/Hexagon profiling 能力记录热点，避免只看总时间。
- **可回溯性：** 原有路径与候选路径可独立选择；记录源码版本、构建参数、内核产物标识和测试输入。每一阶段可单独撤回，不覆盖唯一可用产物。

测试以架构风险为中心，不穷举提示词。先验证单层接口、状态依赖和执行成本，再扩展完整模型；避免在基础接口尚未稳定时启动大规模长测。
